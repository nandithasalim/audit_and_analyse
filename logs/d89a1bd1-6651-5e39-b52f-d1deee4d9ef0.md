Here's the architecture for Problem 3.

**Shape of the system**

Two independent agents talking through a structured contract, not free text. The analyst takes a question and returns a JSON object: a list of atomic claims, each claim carrying one or more citation URLs (or explicitly marked "no citation"), plus a top-level note on anything it couldn't find. The auditor never reads the analyst's prose — it only reads that structured list, which makes independent verification mechanical rather than another round of LLM-guessing-what-was-meant. This structured interface is itself a decision worth defending in DECISIONS.md: free-text claim extraction is the naive approach, and I'd actually build that first, show the auditor missing/misparsing claims because of it, then switch to structured output — that gives you the same "naive fails, fixed version passes" narrative Problem 1 asks for explicitly, applied to Problem 3 even though it isn't required there.

**Analyst pipeline**

Plan → Gather (parallel) → Cross-check → Synthesize → Memory write.

The planner step decomposes the question into sub-questions and identifies entities involved, then checks the memory store for anything already known about those entities before deciding what actually needs a fresh search. Gathering fires search and page-fetch calls concurrently with asyncio rather than one at a time — this is what makes the "run work in parallel" requirement real rather than nominal, and it's also what a two-minute wall-clock ceiling would demand if you take that extension. Cross-checking is a distinct step: any claim sourced from only one page triggers a second, different search before it's accepted at full confidence; if a second source genuinely can't be found, the claim is kept but flagged as single-sourced rather than silently presented as solid. Synthesis produces the structured claims-with-citations output. Memory write extracts durable entity-level facts (with source and date) and upserts them into a small persistent store keyed by canonical entity name — this is separate from caching a question's answer; it's what lets question 7 about an entity from question 2 skip redundant searching and start from what's already known.

**Why the memory design matters for one of the hard extensions**

The brief is explicit that caching an answer doesn't count for the cost-drop extension, but memory that transfers to a new, unseen question does. Because the entity store here holds facts, not answers, a later question that never appeared in training data still benefits — that's what makes it eligible, and it should just fall out of building the core requirement properly rather than needing separate work.

**Auditor pipeline**

For each claim: if no citation, flag immediately, no fetch needed. If cited, fetch the source independently (not reusing the analyst's cached page text — an auditor that shares a cache with the thing it's auditing isn't independent), then classify supported / unsupported / contradicted against that fresh fetch. Aggregate into a per-question report. I'd deliberately keep the analyst realistic rather than sabotaged, so the auditor has genuine work to do, and I'd hold back some of my own credibility check by spot-auditing the auditor itself on a small sample — an auditor that rubber-stamps everything is exactly what the brief says it'll notice.

```python
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity


def select_relevant_chunks(page_text: str, claim_text: str, top_k: int = 3) -> list[str]:
    """Split a fetched page into paragraphs and return only the top_k most
    relevant to claim_text -- so the audit LLM call sees a few relevant
    lines, not the whole page."""
    paragraphs = [p.strip() for p in page_text.split("\n") if len(p.strip()) > 40]

    if not paragraphs:
        return [page_text[:2000]]          # no usable breaks -- just cap the length
    if len(paragraphs) <= top_k:
        return paragraphs                  # short page, nothing to filter

    vectorizer = TfidfVectorizer(stop_words="english")
    vectors = vectorizer.fit_transform(paragraphs + [claim_text])

    claim_vector = vectors[-1]
    paragraph_vectors = vectors[:-1]
    scores = cosine_similarity(claim_vector, paragraph_vectors)[0]

    ranked = sorted(zip(paragraphs, scores), key=lambda x: x[1], reverse=True)
    return [p for p, score in ranked[:top_k]]
```

The `len(p.strip()) > 40` filter is doing real work — splitting on newlines after a scrape tends to produce a lot of junk one-word lines (menu items, button labels), and that filter throws those out before they ever get ranked. `TfidfVectorizer` turns each paragraph and the claim into a vector based on which words they share (weighted by how distinctive those words are), and `cosine_similarity` scores how close each paragraph's vector is to the claim's — so the paragraphs sharing the most distinctive words with the claim rank highest. The two early-exit checks (`if not paragraphs`, `if len(paragraphs) <= top_k`) handle the edge cases where ranking would be pointless — a page with no clean breaks, or a page too short to bother filtering.

This is the piece that finally makes `audit_claim` safe to write for real — `fetch_page_text` gets the raw page, `select_relevant_chunks` narrows it to the few lines that actually matter, and only those go into the judgment call. Want to write `audit_claim` now that this exists?
