# DECISIONS.md

## Architecture

**Analyst**: `plan -> parallel retrieve -> resolve_evidence -> synthesize`, each stage a plain Python function (`src/analyst.py`), not a graph framework. `plan()` first extracts the entities in the question and looks them up in memory (`src/memory.py`) *before* deciding what to search for, so a question reusing an earlier entity gets a narrower plan instead of re-researching from zero. `retrieve()` fires one `call_llm(..., use_web_search=True)` per planned sub-query through a `ThreadPoolExecutor` — real wall-clock parallelism, since the OpenAI client call is a blocking HTTP request. `resolve_evidence()` tags each retrieved result as single- or multi-domain-corroborated (a coarse proxy for "cross-check claims in only one source" — true per-claim clustering across sources was cut for time, see below). `synthesize()` is the only step that produces citable claims, and it never calls web_search itself — every claim's citation traces to exactly one `retrieve()` call, which keeps the run trace legible.

**Memory**: a typed fact graph (`subject, relation, object, source_url, question_id`) in SQLite, not "cache the last answer." The brief's hard bonus is explicit that memory must *transfer* to an unseen question, not just replay a seen one — an atomic-fact store is what lets a later question about a *different* aspect of an already-researched entity (e.g. "who owns Tanishq" after a question about its store count) skip straight to a narrower search. Retrieval is hybrid: SQLite FTS5 (bm25) for exact/near-exact token overlap, blended with a TF-IDF cosine pass over the same fact corpus for fuzzy overlap FTS5's tokenizer misses. Rejected: an embedding store (chromadb/faiss) — better recall on paraphrase, but adds an embedding-model dependency and a vector index for a graph that, in an 8-question run, will hold a few dozen facts; not worth it at this scale, worth reconsidering if this store had to hold thousands of facts.

**Auditor**: independent by construction, not just by intent — it never sees the analyst's prose reasoning about a source, only the claim text and chunks it fetches and ranks itself (`src/fetch.py`, `src/retriever.py`). Verdicts are `supported | unsupported | contradicted | no_citation | unverifiable` — five states, not three, because collapsing "the source doesn't say this" and "the source couldn't be fetched" into one bucket would hide which failure mode is actually happening. It also runs one extra pass (`find_uncaptured_claims`) checking the analyst's prose for factual statements that slipped past its own claim extraction — catching the case where an answer *reads* fully cited but a claim buried in the prose isn't in the structured claims list at all.

**Repair**: bounded to exactly one pass per flagged claim — one targeted re-search, one answer rewrite, no re-audit. An unbounded repair-then-reaudit loop would make cost unpredictable and would let the system converge on a claim that merely *sounds* well-cited rather than one that's actually correct, with the auditor rubber-stamping whatever the loop settled on. This is a smaller promise (`attempted, not reverified`) but an honest one.

## Trade-offs made under the time limit

- **No embedding retriever** anywhere (memory or auditor evidence selection) — TF-IDF only. This is the single biggest quality ceiling in the system; see "Where it breaks" below for the concrete cost.
- **Cross-source corroboration is per-retrieval-call, not per-claim.** A real implementation would cluster individual factual statements across sources and check each one's corroboration independently; this build flags a whole `retrieve()` result as single/multi-source and lets `synthesize()` hedge accordingly. Cheaper, coarser, and it can miss a single uncorroborated number buried inside an otherwise multi-sourced paragraph.
- **`resolve_evidence` doesn't reconcile disagreeing sources automatically** beyond telling `synthesize()` which results are single-source — the actual "pick a number and justify it" reasoning happens inside the synthesize prompt, not as a separate dedicated step. q07 in `questions/questions.yaml` is built specifically to exercise this path.
- **The auditor's page-fetch is `httpx` + `BeautifulSoup`, not `trafilatura`/`readability`.** It will do badly on JS-rendered pages and some paywalls; a fetch failure is reported honestly as `unverifiable` rather than silently skipped.

## How this was tested

The sandbox this was built in (a Claude Cowork cloud container) turned out to have **no outbound network access at all** — confirmed with direct `curl` tests to Wikipedia, Google, DuckDuckGo, and `api.openai.com`, all rejected by an org-level egress proxy policy (`connect_rejected: organization policy`), independent of whether an API key was present. That ruled out testing anything that calls `call_llm()` (plan/retrieve/synthesize/audit/repair) inside this session. What *could* be tested offline and was (`tests/test_offline.py`, all passing): JSON-extraction robustness (`src/jsonutil.py`), the chunking logic (`src/fetch.py`), the memory store's hybrid retrieval end-to-end against a real SQLite DB, and — the useful one — **the TF-IDF chunk-selection limitation, reproduced with realistic synthetic Wikipedia-style paragraphs** rather than asserted from memory. For the claim "Tanishq is owned by Titan Company" against four synthetic chunks (a store-opening blurb, a legal-case summary, the actual ownership sentence, and a market-position paragraph), the chunk that states ownership (`"a subsidiary of the Tata Group's Titan Company"`) ranked **#3 of 4** by TF-IDF cosine score — outranked by a legal-case chunk (score 0.265 vs. 0.189) that repeats "Titan Company" and "Tanishq" densely without stating the relationship at all. Full run in `tests/test_offline.py::test_retriever_known_limitation`. The live end-to-end run (`scripts/run_pipeline.py` against the 8 questions in `questions/questions.yaml`, with real cost/audit numbers) has to happen on a machine with real internet — that's what the README's 5-minute quickstart is for, and where the actual per-question cost table and audit-verdict counts this write-up should eventually cite come from.

## Where it breaks

- **TF-IDF retrieval rewards keyword density over stated relationships** (see above, now empirically reproduced rather than assumed). The practical consequence: the auditor can return `unsupported` for a claim that is in fact true, because the ranker handed it the wrong paragraph — not because the source doesn't support the claim. An `unsupported` verdict from this pipeline means "the retrieved evidence doesn't confirm this," which is a narrower and weaker claim than "this is false," and DECISIONS.md readers / graders should read it that way. The `quote` field in every audit verdict exists specifically so a human can tell the two apart by looking at what was actually retrieved.
- **Single-domain corroboration checking is coarse** (see trade-offs) and can both over- and under-flag depending on how a retrieve() result happens to bundle claims.
- **The repair gate doesn't verify its own fix** — a repaired claim is reported as `attempted`, with the resolution the re-search returned (`confirmed`/`corrected`/`unresolvable`), but is never re-audited, by design (see Architecture). A wrong repair can ship uncaught.
- **No embedding fallback** means any claim whose source phrases the fact very differently than the claim is at risk of a false `unsupported`, not just the worked Tanishq example.

## What's next with two more weeks

Swap TF-IDF for a small embedding model (even a local sentence-transformers model, no new API dependency) in both the memory retriever and the auditor's chunk selection — this is the highest-leverage single change given the failure mode above. Build real per-claim cross-source clustering instead of the per-retrieval-call proxy. Add the "make cost fall while accuracy holds" hard bonus properly: right now memory *should* reduce plan search-query count on repeat entities, but that effect hasn't been measured against a real 8-question run yet — instrument `scripts/cost_report.py` to report search-query count and known-facts-used alongside cost, and plot the trend. Make the analyst adversarial-aware (tell it the auditor is checking every claim, measure whether citation behavior changes for better or worse) — currently unimplemented. Get the whole pipeline running somewhere with real internet and fill in this write-up's cost table and audit-verdict counts with actual numbers instead of the offline unit result above.
